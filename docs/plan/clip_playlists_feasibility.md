# 起止点与片段播放列表：可行性报告

日期：2026-10-16
依据：`master`（b68d5ce）的代码；分支 `feat/start-point` 上只有计划文档的改动

## 结论

可行，不用换播放库，也不用改线程和音频管线的结构。

- 后端只需要补一个能力：让正在播放的音频在指定位置停下。现有的 `EndSignal` 已经按采样数计位置，加一个停止位置就够了。
- 工作量主要在 App 层：把“当前播放的是曲库第几首”换成“当前播放项”（文件加可选的片段），
  以及播放列表的新格式和编辑界面。这些是成片的机械替换加集中换算，现有 122 个 App 测试用的
  假后端可以直接覆盖新行为。
- 播放顺序（`PlaybackOrder`）不用改：它只认“升序的下标列表加当前下标”，播放列表范围直接传条目号即可。

## 1. 已确认的设计

1. 单个录音可以设起点和终点。
2. 播放列表的条目可以是整首，也可以是片段；片段的起止从该文件已有的跳转点里选，时间复制进播放列表。
3. 片段播放和播放列表播放都不读写这个文件的收听进度。
4. 片段播放时显示片段自己的时间（0:00 到片段长度）。
5. 播放列表是一个播放范围，顺序、循环和随机在列表内生效。
6. 分三步做：单个录音的起止点 → 以片段为单位播放 → 播放列表的新格式和编辑界面。
7. 录音自己的起点、终点和播放列表条目的起止互不相干：播放列表里的条目不用录音的起点和终点，
   整首条目从 0:00 放到文件结尾。
8. 每个播放列表各记自己的循环方式，默认播完整个列表停止，按 `z` 切换。随机开关曲库和播放列表共用一个。
9. 用户自己跳到终点之后，放到文件结尾。
10. 跳转点面板里按 `S` 设为或取消终点。
11. 进入列表范围沿用现在的操作：`P` → 选中列表按 Enter → 在某一条上按 Enter。
12. 回到曲库范围后按 `p`（上一首），历史里是播放列表条目时，按原样播这个片段并回到那个列表范围；
    列表或条目已经删掉时只当作插播。

第 7–12 项是看过这份报告初稿后定的（同日），下文已按它们改写。

起点的已定设计（跳转点上的标志、面板里按 `s`、`0` 先回到起点）见 `plan_v2.1.0.md` 的“起点和终点”一节，
这里沿用，只补上终点。

## 2. 现有结构里相关的部分

| 部分 | 现状 | 位置 |
|---|---|---|
| 播放后端 | 只管当前一首；位置、时长、跳转都是整个文件的绝对时间 | `src/player/mod.rs` 的 `PlaybackBackend` |
| 播完的判断 | `EndSignal` 包住解码器，按采样数计位置，解码源耗尽时发 `SourceEnded`；比时长早 1 秒以上结束的判为解码出错 | `src/player/backend.rs` 的 `EndSignal`、`classify_source_end` |
| 输出中断恢复 | 后台新建一个 `Player`，用 `load_at` 装回原位置，成功后把音量、平衡等设置搬过去 | `backend.rs` 的 `start_recovery`、`drain_events` |
| 当前曲目 | `playback.playing_index`，曲库下标，27 处使用 | `src/app/state.rs` |
| 队列、历史 | `VecDeque<PathBuf>`、`Vec<PathBuf>`，22 处使用 | `src/app/state.rs`、`queue.rs`、`playback.rs` |
| 播放范围 | `Catalog::scope()`：文件夹筛选后的曲库下标，升序 | `src/app/catalog.rs` |
| 播放顺序 | `PlaybackOrder` 只接收范围和当前下标，不碰曲库、播放器 | `src/app/order.rs` |
| 播放列表 | v1：`{version, name, tracks: [路径]}`；同一路径不能加两次；播放就是把选中位置之后的路径倒进临时队列 | `src/playlist.rs`、`src/app/playlists.rs` |
| 位置和时长的读取 | 约 30 处：App 里的 `media`、`progress`、`marks`、`sleep`、`session`，界面里的 `now_playing`、`lyrics` 直接读 `app.player()` | 见第 3.3 节 |
| 系统媒体控制 | track_id 是 `/Track/{playing_index}`；长度、位置、SetPosition 用文件时间 | `src/app/media.rs`、`src/media/` |
| 会话 | TOML：曲目路径、位置、文件夹筛选；读取时忽略不认识的字段 | `src/session.rs` |

## 3. 逐项可行性

### 3.1 在指定位置停下（第 1、2 步都要）

做法：

- `EndSignal` 多一个共享的停止位置（`Arc<AtomicU64>`，按采样数），计数到了就当作解码源耗尽，
  照常发 `SourceEnded`。跳转时 `EndSignal::try_seek` 已经会重设计数，停止位置跳转后照样有效。
- 停止位置做成播放中可以改的值，而不是装载时的参数：播放中设或取消终点、跳过终点后取消停止
  （见 3.2），都不用重新装载。后端接口加一个 `set_stop_at(Option<Duration>)`，用文件时间。
- 已在 2.1.0 实现，和这里的设想有一处不同：计数**一路走到**停止位置才停，跳转把计数直接设到它或它之后
  不算。跳过终点因此不用取消停止位置，跳回之前又会停（见 `plan_v2.1.0.md`“起点和终点”第 10 节）。
  第 2 步的片段若要“跳过片段终点也算这一条播完”，由 App 在跳转时按目标位置判断，不改后端。
- `classify_source_end` 要知道这次是停在停止位置的，不能当成“提前结束”报解码错误。
- 输出中断恢复时，新建的 `Player` 要和音量、平衡一起接过停止位置。
- 假后端加同样的接口，测试一侧加“播到某个位置”的控制。

精度：按解码出的采样数算，误差在一帧以内。跳转后的计数按请求的位置推算，压缩格式跳转本身就不精确，
这个误差和现在的位置显示一样，听不出来。

风险：低。改动集中在 `backend.rs` 一个包装器里。

### 3.2 单个录音的起点和终点（第 1 步）

- 终点和起点一样是跳转点上的标志：`marks.json` 里那一条加 `"end": true`。
  `marks.json` 还没随正式版发布过，不用升版本。终点必须在起点之后。
- 播放到终点就是这一首播完：记为听完，按循环方式接下一首，“本条”睡眠定时在终点停，
  淡出按离终点的剩余时间算（`src/app/sleep.rs`）。
- 收听进度“离结尾 3 秒内算听完”改为离终点 3 秒内；`ProgressStore::record` 已经要为起点加参数，
  终点一起传。
- 时间显示仍是整个文件，和已定的起点设计一致：起点之前的开头按 `0` 两次还能听到。
- 只在正常播放越过终点时停；用户自己跳到终点之后就放到文件结尾，片尾还能听到，
  和“起点之前的开头还能听”对称。实现上由后端保证：只有一路播到停止位置才停（见 3.1）。
- 面板里按 `S` 设为或取消终点（`s` 是起点，`e` 已经是改名）。
- 录音的起点和终点只在曲库范围里生效，包括从曲库排进队列的插播；播放列表里不用（见 3.3、3.5）。

这一步不碰播放项和播放列表，可以随 2.1.0 和跳转点一起发布。

### 3.3 当前播放项（第 2 步的核心）

- 新的类型“播放项”：路径加可选的片段（起、止、名称）。队列和历史从路径换成播放项。
- 播放项要记来源。来自曲库的（包括从曲库排进队列的插播）按录音的起点、终点和收听进度播放；
  来自播放列表的只按条目自己的范围播放，不用录音的起点和终点，也不碰收听进度。
- 当前播放项和曲库下标分开存：同一个文件可以在播放列表里出现多次，光凭曲库下标分不清是哪一条。
  曲库下标仍然保留，曲库里正在播放的 ▶ 标记、跳转点、歌词都按它找文件。
- 时间换算放在 App：后端继续用文件时间，App 给出“显示用”的位置和时长（片段内是相对时间）。
  界面、系统媒体控制、`←/→`、`H/L`、`0–9`、鼠标点进度条都改走它；跳转点、歌词（LRC 时间戳是文件时间）、
  收听进度继续用文件时间。界面里直接读 `app.player().position()` / `duration()` 的地方
  （`src/ui/now_playing.rs`、`src/ui/lyrics.rs`）改为向 App 要。
  - 也可以让后端直接报片段内的相对时间，但歌词、跳转点、频谱都按文件时间，换算会散到更多地方。
- 片段内的跳转：后退到片段开头为止；越过片段结尾就是下一项。现在 `seek_rel_micros` 越过文件结尾时
  已经是“记听完、下一首”，换成片段结尾即可（片段不记听完）。`0` 回片段开头；
  列表里的整首条目按 `0` 回到 0:00，不经过录音的起点。
- 片段的结尾是硬的（越过就下一项），和 3.2 的软终点不同。
- 片段播放时，跳转点只显示片段内的，位置换算成相对时间；`b` 照样按文件时间记。
- 收听进度：在播放列表范围里播放时，`note_progress`、`mark_finished`、`resume_point` 都不动收听进度。
- 系统媒体控制：track_id 改成按播放项编号。同一个文件的两个片段先后播放时，桌面小组件要知道换了曲目，
  才会刷新长度。长度、位置、SetPosition 都用片段时间。片段有名字时标题为“文件名 · 片段名”；
  隐私模式照旧只给通用标题。

改动面：`playing_index` 27 处、队列和历史 22 处、位置和时长约 30 处，集中在 `src/app/` 的
`playback`、`queue`、`media`、`progress`、`marks`、`sleep`、`session`，以及界面的
`now_playing`、`lyrics` 和队列面板。这是三步里最大的一块，但都在主线程里，不涉及音频线程。

建议先做一次不改行为的重构：队列和历史换成播放项、界面改走 App 的位置和时长，现有测试一行不改全部通过，
再加片段的行为。抽 `file_records` 时就是这样做的。

### 3.4 播放列表作为播放范围

- `PlaybackOrder` 不用改：播放列表范围传 `0..条目数` 和当前条目号，顺序、列表循环、单曲循环、
  随机袋都照常工作。播放列表范围用自己的 `PlaybackOrder`，改文件夹筛选时不会洗掉列表的随机袋。
- 播放范围变成两种：曲库（含文件夹筛选）和播放列表。`advance`、`can_go_next`、会话保存按范围分开处理。
- 进入范围沿用现在的操作：`P` 打开播放列表面板，选中列表按 Enter 查看条目，在某一条上按 Enter
  从这里播放。现在这一步是把后面的条目倒进临时队列，改为进入列表范围、从这一条开始。
- 离开范围：在曲库里按 Enter（或双击）播一首，就回到曲库范围。队列里的条目是插播，播完回到原来的范围，
  和现在一样。“正在播放”区显示“列表 睡前 3/12”。
- 循环方式：每个播放列表各记自己的，存在播放列表文件里（见 3.5），新建和从 v1 转换来的列表默认“顺序”，
  即播完整个列表停止。在列表范围里按 `z` 切换的是这个列表的循环方式，改了就写盘，曲库的不变。
  系统媒体控制报告当前范围的循环方式，从系统那边改循环时也改当前范围的。
- 随机开关曲库和播放列表共用一个，照旧存在配置文件里。
- 历史里的条目记着来源：回到曲库范围后按 `p` 退到一个播放列表条目时，按原样播这个片段并回到那个列表范围，
  当前条目落在它上面；列表或条目已经删掉时只当作插播。
- 播放中编辑正在播放的列表（删除、移动、添加）时条目号会变：给每个条目一个内存里的编号，编辑后按编号找回
  当前条目、重洗随机袋。这和现在重扫后按路径找回 `playing_index` 是同一种做法。
- 会话：加列表名称和条目号，位置存片段内的时间。旧版本读到时会忽略这两个字段，只恢复文件和位置。

### 3.5 播放列表的新格式和编辑（第 3 步）

v2 格式：

```json
{
  "version": 2,
  "name": "睡前",
  "repeat": "none",
  "entries": [
    {
      "path": "/home/tyzq/Music/ASMR(Rica)/A.m4a",
      "file_size": 123456789,
      "modified_ns": 1760000000000000000,
      "start_ms": 750000,
      "end_ms": 1820500,
      "name": "掏耳"
    },
    { "path": "/home/tyzq/Music/ASMR(Rica)/C.flac", "file_size": 2345678, "modified_ns": 1760000000000000000 }
  ]
}
```

- `repeat` 是这个列表的循环方式，取值和配置文件的 `repeat` 相同（`stop` / `none` / `all` / `one`），默认 `none`。
- 没有 `start_ms` / `end_ms` 的条目是整首，从 0:00 放到文件结尾，不用录音自己的起点和终点。
- 读到 v1 时自动转成整首条目，第一次改动时写成 v2。旧版本读到 v2 会提示无法读取并跳过，不会改写它。
- 存 `file_size` 和 `modified_ns`：文件改名后，播放列表能像收听进度和跳转点一样跟过去。匹配规则沿用
  `file_records`，但播放列表是有顺序、可重复的条目，要另写按条目搬的版本。现在播放列表不跟随改名；
  片段是花了功夫配的，丢了可惜。
- 允许同一个文件出现多次。
- 文件被剪短后：片段起点超出时长的跳过并说明，终点超出的截到文件结尾。
- 编辑界面：
  - 加片段：最顺手的入口是跳转点面板（`B`）。选中一个跳转点按一个键，把从它到下一个跳转点
    （后面没有跳转点时到文件结尾）的一段加进播放列表，再选加到哪个列表。时间在这时复制进列表，
    之后改动或删除跳转点不影响已经加好的片段。曲库里的 `a` 照样加整首。
  - 列表条目面板：`J/K` 移动（队列面板已有同样的操作）、`d` 删除、`e` 改名，以及改起止：列出这个文件的
    跳转点（加上 0:00 和结尾），挑起点和终点。文件不在播放也能编辑：跳转点可以按路径直接从 `MarkStore` 取。
- 顺手要修的两处现有问题：
  - 读不了的播放列表文件只是跳过；之后新建一个同名列表，会按名字算出同一个文件名，直接覆盖它。
    片段列表值得和收听进度一样的保护：读不了就改名保留，不覆盖。
  - 列表条目面板每画一帧都对每一行调用 `path.is_file()`。队列面板已经改成按曲库解析
    （`resolve_queue_rows`），列表面板照做。

## 4. 风险

设计上的问题都已定下（第 1 节）。剩下的是实现上要留意的：

1. 片段之间不是无缝衔接：每一项都要重新装载再跳转，切换时有短暂的空隙，和现在切歌一样（没有实测）；
   同一个文件里相邻的两个片段也是如此。对 ASMR 影响不大；要无缝得预先装好下一项，不在这次的范围。
2. 循环方式存在播放列表文件里，按 `z` 就要写一次播放列表文件。写不了时提示，内存里照样切换，
   下次改动时再写，和跳转点的做法一样。
3. 版本：第 1 步可以随 2.1.0；第 2、3 步改了播放列表格式和会话，建议放到 2.2.0。

## 5. 建议的顺序

1. **单个录音的起止点**（2.1.0）：后端的停止位置 → 跳转点上的起点、终点标志 → 自动从起点开始、`0`、
   软终点、收听进度 → 面板和文档。
2. **以片段为单位播放**：不改行为的重构（播放项、显示用的位置和时长）→ 播放列表 v2 格式
   （片段范围、每个列表的循环方式、从 v1 转换、读不了不覆盖）→ 片段播放（硬结尾、相对时间、
   系统媒体控制）→ 播放列表范围和它的循环方式。列表范围要把循环方式存进列表文件，所以 v2 格式提前到这一步。
3. **播放列表的编辑**：改名跟随 → 编辑界面（加片段、移动、改起止、改名）→ 文档。

每一步照旧单独提交，提交前在 dev-fedora 容器里通过 fmt、clippy 和全部测试。
